# 企业微信预约填报通知系统

自动监控客户经理次日预约填报情况，按时向企业微信发送提醒和通报。

---

## 通知时间表

除周通报外，所有通知**仅周一至周五发送**（周末不产生预约）。共 24 个定时任务：22 个受工作日限制，2 个为周通报。

| 通知类型 | 发送时间 | 发送对象 | 触发条件 |
|---|---|---|---|
| 客户经理个人提醒 | 18:00 / 18:45 / 19:15 / 19:45 / 20:15 / 21:00 / 22:00 / 23:00 | 各客户经理（个人） | 未达 2 户才发，达标跳过 |
| 简洁通报（张端） | 18:30 / 19:00 / 19:30 / 20:00 / 20:30 / 21:00 / 21:30 | 张端副经理 | 仍有人未填时发送 |
| 简洁通报（钟俊杰） | 19:00 / 19:30 / 20:30 / 21:00 / 21:30 | 钟俊杰经理 | 仍有人未填时发送 |
| 详细通报 | 22:00 | 全体管理者 | 工作日固定发送 |
| 最终数据收集 | 23:30 | —（不发消息） | 判定填报状态，写入统计表 |
| 周通报 | 周三 12:15 / 周日 12:00 | 全体客户经理 + 管理者（14 人） | 固定发送，**不受工作日限制** |

每个配置的通知时间点先独立从金山文档同步一次最新数据，再发送该时间点的通报；不同时间点不复用数据。同一时间点若有多个通报任务，则共用该时间点的同步结果。金山脚本回调默认最多等待 30 秒，超时不使用旧数据发送。

---

## 目标日期与考核窗口

通报针对的是「下一个工作日」的预约，周五顺延到下周一：

| 发送日 | 目标日期 | 考核窗口 | 消息措辞 |
|---|---|---|---|
| 周一 ~ 周四 | 次日 | 目标日当天 | 明日 |
| 周五 | 下周一 | **周六 ~ 周一，三天合计** | 周末至下周一 |

周五按三天窗口计数，是因为部分客户经理周末也上班、可能在周末安排走访。只要周六、周日、周一加起来够 2 户即算达标，周五的提醒里日期行会显示为 `📅 日期：2026-08-08 ~ 2026-08-10（三天合计）`。

日期逻辑集中在 `reporter.py` 的 `next_workday()` / `target_window()` / `records_in_window()`，`scheduler.py` 与 `api.py` 都调用同一份实现。

### 群内 @ 机制

企业微信群机器人只支持两种 @ 方式，`sender.py` 中 `wecom_userid` 优先，为空时回退到 `mobile`：

| 字段 | 对应载荷 | 说明 |
|---|---|---|
| `wecom_userid` | `mentioned_list` | 企业微信管理后台 → 通讯录 → 成员详情中的账号，最稳定 |
| `mobile` | `mentioned_mobile_list` | 需与成员企业微信绑定手机号一致，换号或未绑定会静默失效 |

> 手机号与绑定号不一致时，企业微信仍返回 `errcode: 0`，但实际没人被 @，日志里看不出异常。想彻底避免请填 `wecom_userid`。群机器人的 webhook key **不能**用于调用「手机号获取 userid」接口（`/cgi-bin/user/getuserid` 返回 `40014 invalid access_token`），该接口需要企业自建应用的 corpid + corpsecret 且具备通讯录读取权限，只能在管理后台手工查。

## 手动发送通报（前端「发送通报」Tab）

选好规则和日期后自动预览，预览出来的正文和收件人都可以改：

| 操作 | 说明 |
|---|---|
| 勾选接收人 | 按「客户经理 / 管理者 / 测试」三组展示，点姓名切换。支持整组切换、全选、清空、恢复「默认」 |
| 编辑正文 | 点「编辑」切成文本框，改完可点「恢复原文」回到模板生成的内容 |
| 发送 | 确认弹窗会先列出这次会 @ 到谁 |

要点：

- 一旦手动改过勾选，之后换日期/换规则不会再被规则默认覆盖，除非点「默认」。同理，正文编辑过后重新预览也不会被覆盖。
- **不选任何人**时消息照发到群里，只是不 @ 任何人 —— 想安静地补发一条通报时用这个。
- 姓名旁的红色 `!` 表示该成员在 `config.py` 里既没有 `mobile` 也没有 `wecom_userid`，@ 不到。
- 规则条件未触发（比如全员已达标）时预览是空的，此时可以点「编辑」自己写正文强制发送；正文为空会被后端拒绝（400）。
- 后端只接受姓名（`recipient_names`），手机号/userid 一律从 `config.py` 现查，前端改不了。

验证 @ 能否真正触发提醒：规则随便选一个 → 清空 → 只勾「测试 / 李璇」→ 编辑正文写一句测试内容 → 发送。

## 通报示例

### 1. 客户经理个人提醒（发给本人）

```
📋 @麦海芬

明日预约填报提醒（第2次）
📅 日期：2026-08-04
✅ 已填：1 户
⚠️ 还需：1 户

📊 本月记录：
   ⏱️ 超时填报：3 次
   ❌ 漏填：1 次

💡 温馨提示：请尽快完成填报，确保明日工作顺利开展~
```

开启「应缴账单」后，在温馨提示**之前**插入：

```
☕ 下午茶基金提醒：
   · 本月漏填 1 次（× 10 元/次）= 10 元
   请上交 10 元至部门下午茶基金。
```

开启「规则警示」后，在温馨提示**之后**追加：

```
☕ 下午茶基金规则：
   · 漏填（23:30 仍不足 2 户）：每次上交 10 元
   · 超时填报（19:30 后才填满 2 户）：每累计 5 次上交 10 元
   · 按自然月统计，次月归零。19:30 前填满即完全不计。
   ⚠️ 本月已超时 4 次，再超时 1 次就要上交 10 元
```

> 已填报 ≥ 2 户时本条消息不发送。"本月记录"仅在有超时或漏填时显示。两个基金开关的差别见下文。

## 填报状态说明

| 状态 | 判定条件 |
|---|---|
| 准时（on_time） | 23:30 前已填 ≥ 2 户，且最后一条记录上传时间 ≤ 19:30 |
| 超时（overtime） | 23:30 前已填 ≥ 2 户，但最后一条记录上传时间 > 19:30 |
| 漏填（missing） | 23:30 时仍未达到 2 户 |

## 下午茶基金（两个独立开关）

计费标准统一如下，改 `reporter.py` 顶部的 `FINE_PER_MISSING` / `FINE_PER_OVERTIME_LOT` / `OVERTIME_LOT_SIZE` 即可，两处文案都会跟着变：

| 触发条件 | 金额 |
|---|---|
| 本月漏填 N 次 | N × 10 元 |
| 本月超时填报累计满 5 次 | 每满 5 次 10 元 |

前端「系统」Tab 提供两个开关，都只作用于**客户经理个人提醒**，相互独立、可单开可同开：

| 开关 | 设置键 | 定位 | 显示条件 | 内容 |
|---|---|---|---|---|
| 📢 规则警示 | `fine_rules_enabled` | 事前警醒 | 开启即显示 | 讲清规则 + 「再超时几次就要上交」，**不报欠款金额** |
| 💸 应缴账单 | `fine_enabled` | 事后账单 | 当月确有欠缴才显示 | 算出本月已欠多少钱并要求上交 |

规则警示的**前 3 行固定**（就是规则本身），**末尾的警告行随当月记录变化** —— 这是它比干讲规则更有警醒作用的地方。超时与漏填各自独立成行，两项都有就出两行：

| 当月超时 | 当月漏填 | 输出的警告行 |
|---|---|---|
| 0 ~ 2 次 | 0 次 | `✅ 本月暂无欠缴记录，今天按时填报即可继续保持` |
| 3 次 | 0 次 | `⚠️ 本月已超时 3 次，再超时 2 次就要上交 10 元` |
| 4 次 | 0 次 | `⚠️ 本月已超时 4 次，再超时 1 次就要上交 10 元` |
| 5 ~ 7 次 | 0 次 | `⚠️ 本月已超时 5 次（满 5 次），已产生 10 元` |
| 0 次 | N ≥ 1 | `⚠️ 本月已漏填 N 次，今天再漏一次将再加 10 元` |
| 4 次 | 2 次 | 上述两行**都出**：先超时行，再漏填行 |

超时行的三种形态对应三个阶段：

| 阶段 | 判断 | 用意 |
|---|---|---|
| 离下一档还差 1~2 次 | `to_next_lot <= 2` | 临界警告，最有效 |
| 已满档（5、10 次…） | `lots_owed >= 1` | 已经产生费用，必须说清已欠多少 |
| 刚满档后的缓冲区（6、7 次） | 同上 | 仍按已满档提示 |
| 离下一档还差 3~4 次 | 都不满足 | 不提示，避免每天刷同一句让人免疫 |

> 漏填只要 ≥ 1 次就提示，因为漏填当场就产生费用，没有「攒够几次」的缓冲。
>
> 注意末行只会在「超时 0~2 次**且**漏填 0 次」时才是那句 `✅`。早期实现里超时刚好是 5、6、10 次时会错误地显示「暂无欠缴」（`to_next_lot` 满档后重置为 5，警告不触发就落到了兜底那句），已修正为上表的「已产生 N 元」。

两个开关都存在 `app_settings` 表，重启后保持。`POST /api/config/settings` 只写传了的字段，未传的保持原值，所以可以单独改一个。

## 调度器状态持久化

调度器开关存在 `app_settings` 表的 `scheduler_enabled` 键里，**只需要开一次**：之后重新部署、进程崩溃、机器重启都会在 `lifespan` 启动时自动恢复到停机前的状态。点了「停止」则重启后保持停止。

`/api/scheduler/status` 返回两个字段，排查时看这两个是否一致：

| 字段 | 含义 |
|---|---|
| `running` | 当前进程里 APScheduler 实例是否活着 |
| `desired` | 落库的开关意图，也就是重启后会恢复成什么状态 |

任务本身仍是内存态（`BackgroundScheduler` 无 jobstore），进程起来时按 `scheduler.py` 的规则重新注册，所以改了时间表重启即生效。作业默认参数：

| 参数 | 值 | 作用 |
|---|---|---|
| `misfire_grace_time` | 600 秒 | 重启恰好压在触发点上时仍能补发；默认值只有 1 秒，任务会被静默丢弃 |
| `coalesce` | `True` | 停机期间攒下的多次触发只补最后一次，不会连发一串 |
| `max_instances` | 1 | 同一任务不并发执行（金山同步是阻塞的，最长 8 分钟） |

> 停机超过 10 分钟的时间点不会补发，这是有意的 —— 补一条早已过时的督办消息没有意义。

## 常用 API

| 方法 | 路径 | 说明 |

## 运行日志

前端「运行日志」Tab 展示每次消息发送的结果，数据来自 `send_logs` 表：时间、规则、状态、接收人、消息摘要、错误。表格中长内容会截断，**点击任意一行**可弹窗查看完整消息正文和错误堆栈。

分页：底部提供首页/上一页/页码/下一页/末页，页码窗口最多 5 个、随当前页滑动；每页可选 20/50/100/200 条，切换每页条数会回到第 1 页。顶部的总计/成功/失败是**全量统计**，不随翻页变化。日志在浏览期间被清理导致当前页越界时会自动回落到末页。

## 历史记录清零

需要设定「从某天开始计算，之前的漏填/超时一律免除」时，用 `reset_history.py`，把该日期之前的 `overtime` / `missing` 记录改为 `on_time`：

```bash
# 预览（默认 dry-run，只打印将影响的记录）
python -m wecom_notice.reset_history --before 2026-08-04 --archive-visits

# 确认后执行，会先自动备份数据库到 runtime/backup/
python -m wecom_notice.reset_history --before 2026-08-04 --archive-visits --apply
```

| 参数 | 说明 |
|---|---|
| `--before` | 起算日，**不含**当天。`--before 2026-08-04` 会保留 08-04 的记录。默认今天 |
| `--apply` | 真正写入；不加则只预览 |
| `--archive-visits` | 同时归档起算日前的 `visit_records` |

`--archive-visits` 建议一并使用：`fill_statistics` 为空时部分汇总会从 `visit_records` 反推历史漏填，只清 `fill_statistics` 的话记录可能重新长回来。

执行前先停掉调度器，避免与 23:30 的最终数据收集任务撞上。
